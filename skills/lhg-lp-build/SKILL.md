# lhg-lp-build：落地页高保真实现

> 目标：把线框变成能上线的高保真页面。
> 核心纪律：**静态先行、文案真实、性能是功能的一部分。**

## 1. 何时使用

- 线框已确认、设计令牌已定 → 加载本 skill 开始写代码
- 存量落地页打开慢、SEO 差 → 用第 4-5 节做性能与 SEO 改造
- 表单收不到数据、按钮点了没反应 → 看第 6 节

## 2. 技术选型

落地页不需要重型框架，按场景选：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 单页、快速验证 | 纯 HTML + Tailwind（CDN 或构建版） | 零构建、秒部署，一个文件拎走即用 |
| 多页面/需组件复用 | 静态站点框架（如 Astro） | 组件化但不输出多余 JS |
| 已有 Next.js 项目 | 复用现有项目 | 别为落地页另起一套工程 |

默认选第一行：**纯静态优先**。落地页的使命是快和稳，不是炫技。
选了重型方案要写出理由，否则打回。

## 3. 六步实现流程

### 第一步：设计令牌落地
把 `lhg-lp-design` 第 4 节的令牌写成独立文件（CSS 变量或主题配置）。
先写令牌文件，再写任何组件——顺序反了就容易到处硬编码。

### 第二步：静态骨架
按线框搭 HTML 结构，先不填文案、不加样式、不写交互。
用语义化标签：header / main / section / footer。一个页面一个 h1。

### 第三步：填真实文案
把 `lhg-lp-strategy` 的文案包填进去。填的时候逐条问自己：
这个数字有出处吗？这条评价是真的吗？这个 logo 真合作过吗？
答不上来 → 换成诚实占位（标灰"待补充"），不许编。

### 第四步：交互
落地页的交互只做三件：锚点平滑滚动、FAQ 折叠、表单提交。
- 锚点滚动：CSS scroll-behavior 就够，别引动画库
- FAQ 折叠：用原生 details/summary，零 JS、可访问性白送
- 表单提交：见第 6 节

不需要的交互一律不做：轮播图、视差滚动、满屏动画——
这些对转化没帮助，只增加翻车概率。

### 第五步：动效（克制）
- 只给 CTA 加 hover 状态（颜色加深/轻微上浮，二选一）
- 页面滚动渐入：只用在首屏以下区块，且时长 ≤300ms
- 全页支持 prefers-reduced-motion

### 第六步：自查
跑一遍确定性审计脚本，修掉所有 blocker；再按 `lhg-lp-audit` 第 5 节做人工评审。
没过自查的页面不许交付。

## 4. 性能基线（硬指标）

1. 首屏加载 < 3 秒（4G 网络）：图片是最大头，见下。
2. 图片：首屏大图用现代格式、加宽度高度防抖动；首屏外的图全部 loading="lazy"；
   有条件的加 srcset（至少 1x/2x 两档）。
3. 字体：系统字体优先；必须用自定义字体时只引需要的字重，加 font-display: swap。
4. 第三方脚本：统计代码只加一个，放在页面底部；不许加用不上的 SDK。
5. 总 JS < 100KB（纯静态页目标 < 30KB）：落地页不需要框架运行时。

## 5. SEO 基线

1. `<title>`：产品名 + 核心价值，一句话。
2. `<meta name="description">`：60-150 字，含核心关键词和行动召唤。
3. 语义化标签 + 唯一 h1（见第二步）。
4. OG 标签（og:title / og:description / og:image）：分享到社交平台时不至于一片空白。
5. 图片 alt 全覆盖（装饰图 alt 留空）。

## 6. 表单与转化组件规范

表单是落地页的钱袋子，按最高标准做：

1. **字段 ≤3 个**：每多一个字段转化率就掉一截。只留行动必需的。
2. **每个输入框配可见 label**：placeholder 不算 label（一点就没）。
3. **提交按钮文案**：动词+利益（"免费试用 14 天"），不许"提交"。
4. **提交后**：明确的成功态（"已收到，我们会在 24 小时内联系你"），
   不要只弹一个"提交成功"就没了。
5. **报错友好**：错了告诉用户错在哪、怎么改，不要只变红。
6. **防死链**：每个 CTA 都有真实去向；表单后端没接好之前，
   按钮先链到"联系方式"区块，不许 href="#"。

## 7. 部署前文件检查

- [ ] 无 lorem ipsum、无 TODO/FIXME 残留
- [ ] 无硬编码色值（令牌文件除外）
- [ ] 无紫粉渐变/渐变标题字/emoji 泛滥
- [ ] 所有图片有 alt、有尺寸、防抖动
- [ ] title / description / OG 已填
- [ ] favicon 已加
- [ ] 表单走完全流程实测通过

## 8. 从落地页升级到完整应用（衔接 lhg-fullstack）

落地页验证成功后，业务往往会长出"应用"需求。用以下信号判断升级时机：

1. **用户体系**：需要注册/登录、记住用户状态 → 落地页装不下了
2. **数据沉淀**：表单数据要存库、要后台查看/导出 → 该上数据库了
3. **交易闭环**：要在线支付、对账、订单管理 → 必须上后端
4. **内容膨胀**：页面超过 5 个、需要站内导航体系 → 该做多页应用了

升级路径：保留本 skill 沉淀的卖点卡片、设计令牌、文案包（这些是应用的"脸"），
把实现层整体迁移到 `lhg-fullstack`（它的 `lhg-fs-plan` 会接管架构规划）。
**不要**在落地页代码上直接加数据库——单文件页面加后端等于在沙子上盖楼，
重写比嫁接便宜。

## 9. 反模式

- ❌ "先上框架，以后好扩展"——落地页以后要扩展就说明它该升级成应用了，
  到时候用 lhg-fullstack 重做，别现在过度设计
- ❌ 引一堆动画库让页面"生动起来"——生动不转化，清晰才转化
- ❌ 图片直接扔 5MB 原图——先压缩，再谈设计
- ❌ 表单 8 个字段"顺便收集点信息"——顺便的代价是转化率

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 审计脚本 blocker 清零了吗？→ 没清零不许交付。
2. 首屏 3 秒能加载完吗？→ 超了就砍图片和第三方脚本。
3. 表单从填到提交走过一遍吗？→ 没走过不算完。
4. 文案里每个数字都能找到出处吗？→ 找不到就删掉。

标准冒烟用例：用"个人作品集首页"走一遍六步流程，
检查 7 条部署前文件检查是否全绿。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-landing-page/issues，
正文写清"输入 → 错误输出 → 期望输出"。
