# lhg-lp-audit：落地页转化自检

> 目标：页面上线前，把"不转化"的坑一个个排掉。
> 核心纪律：**机器查确定的，人查不确定的；blocker 清零才算做完。**

## 1. 何时使用

- 落地页写完、准备交付/部署前 → 必加载
- 已有落地页转化差、想诊断问题时 → 用第 4-5 节逐项排查
- 评审别人做的落地页时 → 直接用第 5 节清单打分

## 2. 双轨自查

1. **机器轨**：跑插件自带的确定性审计脚本（31 条规则，零成本、秒出结果）：
   ```
   python3 scripts/audit/landing_audit.py --target <页面目录> --format text
   ```
   规则覆盖：CTA（行动召唤）/ 信任（社会证明）/ 模板相 / 响应式 /
   可访问性 / SEO / 性能 / 诚实 / 区块完整性 / 文案。
2. **人工轨**：第 5 节清单，查脚本抓不到的东西（文案真实性、视觉层级、真实手感）。

两轨都绿了才算过。只跑脚本不人工，等于只查了一半。

## 3. 发现分级

- **blocker（必须修）**：全页无 CTA、可疑数字声明、紫粉渐变、lorem ipsum 残留。
  这类问题上线后直接伤害转化或品牌，不接受豁免。
- **warning（修或写豁免理由）**：首屏 CTA 过多、表单字段过多、死链 CTA、
  缺社会证明、虚假紧迫感、无联系方式、硬编码色值、emoji 泛滥、固定大宽度、
  图片缺 alt、SEO 缺项、h1 问题、TODO 残留、首屏标题空洞。
  修掉；修不掉的写理由 + 有效期。
- **nit（顺手修）**：CTA 文案无力、渐变标题字、表单控件无标签、无语义化标签、
  图片未懒加载、无响应式图片、缺 FAQ/定价/页脚、页眉无 CTA。

**红线**：为清零而改脚本规则或阈值 = 作弊，不许。

## 4. 五维转化 checklist

这是人工评审的骨架，每维 3 个检查点：

### 维一：首屏 CTA 是否唯一突出
- [ ] 首屏只有一个主 CTA，且是全页视觉最突出的元素（尺寸/颜色/位置三占其二）
- [ ] CTA 文案是"动词+利益"（如"免费试用 14 天"），不是"点击/提交"
- [ ] 3 秒测试：遮住 logo 给没看过的人看 3 秒，他能说出"这是干什么的、点哪里"

### 维二：社会证明
- [ ] 有至少一种社会证明：用户评价 / 客户 logo / 媒体报道 / 认证 / 真实数字
- [ ] 评价带名字和身份（"阿哲，咖啡馆主"比"某用户"可信 10 倍）
- [ ] 所有数字都能说出出处；说不出的已删掉或标"待补充"

### 维三：信任背书
- [ ] 页脚有真实联系方式（电话/邮箱/微信至少一个）
- [ ] 定价透明：价格、包含什么、不包含什么，一目了然
- [ ] 风险逆转：退款政策 / 免费试用 / 随时退订，至少占一条

### 维四：加载性能
- [ ] 手机 4G 下首屏 3 秒内可见
- [ ] 图片已压缩、首屏外懒加载、无 1MB 以上的单文件
- [ ] 第三方脚本 ≤2 个（统计 + 必需品），且在底部加载

### 维五：移动端首屏
- [ ] 390px 宽度下首屏完整：标题、副标题、CTA 全可见，无需横滑
- [ ] 无横向滚动条；按钮触摸目标 ≥44px
- [ ] 字号在手机上可读（正文 ≥14px，标题有层级）

评分：每维 3 分，满分 15。12 分以上通过，9-11 分修完 warning 再测，
9 分以下回炉（先回 `lhg-lp-strategy` 重新提炼卖点）。

## 5. 人工评审清单（脚本抓不到的）

1. **文案真实性**：每个数字、每条评价、每个 logo，逐条问出处。
2. **视觉层级**：眯眼看页面，最先跳出来的元素是不是 CTA？不是就调。
3. **信息气味**：从广告/搜索点进来的人，首屏和他点的入口味道一致吗？
   不一致（标题党）→ 跳出率爆炸。
4. **表单实测**：从填到提交完整走一遍，报错信息是否告诉用户怎么改。
5. **滚动动线**：从上往下滑一遍，每个区块的结尾都有"继续往下"或 CTA 的理由吗？
6. **竞品对比**：遮住 logo，和竞品落地页放一起，用户分得清吗？分不清 → 差异化没讲透。

## 6. 报告模板

自查报告存为 `docs/audit-YYYYMMDD.md`：

```
# 落地页自查报告（YYYY-MM-DD）
- 页面：<路径/链接>
- 结论：通过 / 不通过

## 机器审计
- blocker=X warning=Y nit=Z（附脚本输出摘要）

## 五维 checklist（15 分制）
- 首屏 CTA：x/3 / 社会证明：x/3 / 信任背书：x/3 / 加载性能：x/3 / 移动端首屏：x/3
- 总分：x/15

## 人工评审发现
- ...

## 需人工处理
- ...（如真实文案、真实图片、备案）

## 下一步
- ...
```

结论只能是"通过"或"不通过"，不许写"基本通过""大致没问题"。

## 7. 边界：落地页 vs 完整应用

本自查只覆盖**营销落地页**。如果页面里出现了以下东西，
说明它已经超出落地页范畴，改用 `lhg-fullstack` 的审计流程：

- 用户登录/注册体系、多角色权限
- 数据库读写、复杂业务状态机
- 支付对接、订单系统
- 超过 5 个页面的站内跳转体系

发现越界时明确告诉用户："这已经是个应用了，落地页的 checklist 不够用，
建议切到 lhg-fullstack。"

## 8. 反模式

- ❌ "脚本全绿就等于高转化"——脚本只查确定的，文案烂它查不出来
- ❌ warning 全写豁免理由——豁免是给真修不掉的，不是给懒的
- ❌ 评审只看桌面端——一半流量在手机上，手机没看等于没评
- ❌ 报告写"基本通过"——通过就是通过，不通过就列出差在哪

## 9. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 机器和人工两轨都跑了吗？→ 只跑一轨不算完。
2. blocker 清零了吗？→ 没清零就说"通过"是撒谎。
3. 报告存档了吗？→ 没存 docs/audit-日期.md 等于没做。
4. 发现越界（完整应用）时明确提示用户了吗？→ 没提示就是失职。

标准冒烟用例：拿 fixtures/landing-bad 跑一遍本 skill，
检查是否输出"不通过"报告且 blocker 清单与脚本一致。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-landing-page/issues，
正文写清"输入 → 错误输出 → 期望输出"。
